# WikiBrain

한국어 위키백과 문서 770,097개를 의미 임베딩으로 3D 공간에 펼친 지도입니다. 브라우저에서 77만 개의 별을 돌려 보고, 별을 누르면 그 문서와 링크로 이어진 문서가 보입니다. 올가미로 한 구역을 고르면 그 문서들을 문맥으로 로컬 LLM에 질문하는 RAG 백엔드가 붙어 있습니다. 모든 계산은 8GB Apple Silicon Mac 한 대에서 돌렸고, 외부 유료 API는 쓰지 않습니다.

## 화면에서 할 수 있는 것

- 드래그로 회전, 휠로 확대. 링크가 적은 문서는 멀리서는 숨었다가 가까이 가면 나타납니다.
- 별을 클릭하면 제목, 첫 문단, 들어오는 링크 수가 나오고 링크로 이어진 문서까지 금색 선이 그어집니다.
- Shift+드래그로 올가미를 그리면 안에 든 문서를 고릅니다. 77만 점 투영에 약 64ms 걸리고, 결과는 링크가 많은 순으로 300개까지 남깁니다.

화면은 사막 톤으로 꾸몄습니다. 배경 #18110B에 모래색 별, 셰이더에서 직접 계산한 황토색 안개를 깔았고, 선택한 별만 금색으로 빛나게 했습니다.

## 어떻게 만들었나

1. 위키백과 덤프(2026-11-01, 1.4GB)에서 일반 문서의 제목, 첫 문단 600자, 분류, 본문 링크를 뽑았습니다. 넘겨주기 910,776개를 풀어 링크 12,143,422개를 문서 번호로 연결했습니다.
2. 제목, 첫 문단, 분류를 이어 붙여 `intfloat/multilingual-e5-base`로 임베딩했습니다(768차원, float16, 1.18GB). 8GB 램에서 터지지 않게 4,096개씩 읽고 저장하며, 중간에 끊겨도 이어서 돌아갑니다.
3. 들어오는 링크가 많은 허브 3만 개만 UMAP으로 3D에 배치하고, 나머지 74만 개는 코사인이 가장 가까운 허브 8개 좌표의 가중평균에 놓았습니다. 77만 개 전체에 UMAP을 돌리면 이 장비에서는 메모리가 모자랍니다.
4. 화면은 three.js `Points` 한 번의 드로우로 77만 점을 그립니다.

x, y, z 축 각각에는 의미가 없습니다. UMAP은 가까운 문서를 가깝게 두는 것만 맞추기 때문에 은하 전체를 돌려도 같은 결과입니다. y축은 원반 모양을 내려고 화면에서 0.35배로 눌렀습니다.

## RAG와 로컬 학습 (백엔드)

`backend/mlx_bridge.py`는 127.0.0.1:8001에만 열리고 모든 요청에 토큰을 요구합니다.

- `/api/embed`: 새 글(뉴스 등)을 은하와 같은 e5 모델로 임베딩하고, 가장 가까운 위키 문서 9개를 돌려줍니다. "GPT-5 공개" 기사를 넣으면 GPT-5.2, GPT-5, GPT-5.1 문서가 나옵니다.
- `/api/rag`: 고른 문서의 본문 앞 2,000자를 모아 문맥을 만듭니다. 본문은 덤프에서 다시 뽑아 SQLite(FTS5)에 넣어 두었습니다(2.7GB). 문맥 조립은 6.5ms입니다.
- `/api/chat`: `mlx_lm.server`로 Qwen2.5-1.5B-Instruct(4bit)에 질문을 보내고 답을 스트리밍합니다.
- `/api/augment`: 고른 문서마다 요약, 비교, 적용 세 가지 질문의 답을 베이스 모델이 직접 만들고, 그 데이터로 LoRA를 45 iter 학습합니다. 문서 5개로 돌렸을 때 다운로드와 증강을 포함해 1,255초 걸렸고, loss는 train 0.33, valid 0.44로 끝났습니다. 8GB에서는 학습하는 동안 채팅 서버를 내리고, 끝나면 새 어댑터를 붙여 다시 띄웁니다.

LoRA는 클러스터의 말투와 답 형식을 맞추는 용도입니다. 문서 5~10개로는 사실이 모델에 들어가지 않으므로 사실은 항상 RAG 문맥으로 넣습니다.

새 글을 은하 안에 놓는 위성 배치 엔진(`src/core/physics/`)도 있습니다. 가까운 위키 문서 9개까지의 목표 거리에 맞춰 Adam으로 위치를 찾고, 위성끼리는 최소 거리 이상 떨어뜨리고, 24시간마다 밝기가 반으로 줄어듭니다. ArXiv와 DART 공시를 가져오는 Vercel 프록시(`site/api/proxy.ts`)와 n8n 워크플로(`backend/n8n_workflow.json`)도 들어 있습니다.

## 실행

Python 3.9.6에서 확인했습니다. numba 0.59가 Python 3.13에서는 빌드되지 않습니다.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

데이터는 저장소에 없습니다. 덤프를 `dump/kowiki.xml.bz2`에 두고 파이프라인을 돌립니다. 임베딩과 배치를 합쳐 8GB Mac에서 몇 시간 걸립니다.

```bash
./run_all.sh
```

```bash
.venv/bin/python server.py
```

http://localhost:8000 에서 화면이 열립니다. 첫 기동은 링크 색인을 만드느라 1분쯤 걸립니다.

RAG 백엔드는 본문 DB를 만든 뒤 따로 띄웁니다.

```bash
.venv/bin/python pipeline/6_bodies.py dump/kowiki.xml.bz2
```

```bash
BRIDGE_TOKEN=$(openssl rand -hex 16) .venv/bin/python backend/mlx_bridge.py
```

## 폴더

```
pipeline/   덤프 파싱 → 링크 그래프 → 임베딩 → 3D 배치 → 배포용 데이터, 본문 DB, 위성 보정
backend/    MLX 브리지(임베딩·RAG·채팅·LoRA), n8n 실행 스크립트와 워크플로
src/        위성 배치 엔진과 자체 테스트
index.html  로컬 화면
server.py   로컬 서버 (127.0.0.1, 허용 목록 밖 경로 404, Host 검사, CSP)
site/       Vercel 정적 배포본과 프록시
docs/       설계서 v1·v2, 개발 노트, 검증 보고
```

## 아직 안 되는 것

- 올가미로 고른 문서에 질문하는 채팅 창이 화면에 없습니다. 지금은 백엔드를 직접 호출해야 합니다.
- 첫 토큰이 문맥 2,000자에서 5.4초, 6,000자에서 15초 걸립니다. 1.5B 모델이 긴 문맥을 읽는 시간 때문이고, 목표였던 3초에는 못 미칩니다.
- `/api/embed`의 77만 건 검색이 4.7초 걸립니다.
- 실제 뉴스로 놓은 위성의 배치 오차(Stress)가 0.15로, 목표 0.10보다 큽니다.
- 허브가 아닌 74만 문서의 좌표는 근사치라서 덩어리 안쪽의 세밀한 구조는 정확하지 않습니다.
- LoRA를 학습하는 동안 스왑이 5GB에서 11GB까지 늘었습니다(본문 추출을 같이 돌린 영향 포함).

검증 항목별 결과는 `docs/v2-phase0-6-report-draft.md`에 있습니다.
